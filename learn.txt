================================================================================
ROADMAP: FROM BACKEND DEVELOPER TO SYSTEMS / DISTRIBUTED-SYSTEMS EXPERT
Goal: be able to build things like Kafka, Redis, Nginx, RabbitMQ, WebSockets.
================================================================================

MINDSET (read this first)
- This is a 3-5 year journey, not a checklist. Don't try to "finish" every stage
  before building. Go DEPTH-FIRST: pick a project, and learn the theory you need
  JUST IN TIME to unblock it. You remember what you use.
- The gap between "knows the concept" and "expert" is: tooling, measurement, and
  correctness testing. Most people skip these. Don't.
- Read production source code and academic papers early, even when it hurts.

--------------------------------------------------------------------------------
STAGE 1 - BECOME AN EXCELLENT PROGRAMMER
--------------------------------------------------------------------------------
Systems language (pick ONE to go deep, know OF the others):
  C     - best for learning what the machine really does
  Rust  - memory safety without GC; the modern infra language
  Go    - fantastic for networked/backend infra (Docker, Kubernetes, etcd)
  C++   - still dominant in databases and high-perf systems
Master: data structures, algorithms, manual memory management, pointers,
        ownership/lifetimes (Rust), the stack vs the heap, undefined behavior.

--------------------------------------------------------------------------------
STAGE 2 - CS FUNDAMENTALS (implement, don't just read)
--------------------------------------------------------------------------------
Data structures: arrays, linked lists, stacks, queues, ring buffers, trees,
  graphs, hash tables, heaps, tries, bloom filters, skip lists, LRU cache.
Algorithms: searching, sorting, DP, graph algos, greedy, string algos,
  hashing (and consistent hashing - critical for sharding).
+ ADD: complexity analysis in practice (why O(1) with a bad constant can lose
  to O(log n)), and cache-aware data structures.

--------------------------------------------------------------------------------
STAGE 3 - OPERATING SYSTEMS  *****
--------------------------------------------------------------------------------
Processes, threads, scheduling, context switching, virtual memory, paging,
TLB, deadlocks, synchronization, mutexes, semaphores, condition variables,
shared memory, file systems, signals.
+ ADD: the page cache, mmap vs read/write, fsync/fdatasync and what "durability"
  really means, copy-on-write, huge pages, NUMA.
+ ADD (tooling): strace, ltrace, /proc, gdb, perf, valgrind, ftrace, eBPF/bpftrace.
Resource: "Operating Systems: Three Easy Pieces" (OSTEP) - free and excellent.
Resource: "Computer Systems: A Programmer's Perspective" (CSAPP).

--------------------------------------------------------------------------------
STAGE 4 - COMPUTER NETWORKS  *****
--------------------------------------------------------------------------------
TCP, UDP, IP, DNS, HTTP/1.1, HTTP/2, HTTP/3 (QUIC), TLS/SSL, routing, ports.
+ ADD: TCP internals - 3-way handshake, flow control, congestion control
  (slow start, Nagle's algorithm, delayed ACK), backpressure, head-of-line
  blocking, MTU, Nagle vs TCP_NODELAY.
+ ADD: the C10k / C10M problem and why it drove epoll/kqueue/io_uring.
+ ADD (tooling): Wireshark, tcpdump, ss/netstat, ping/traceroute, curl -v.
Resource: "Beej's Guide to Network Programming" (free).
Resource: "Computer Networking: A Top-Down Approach" (Kurose & Ross).

--------------------------------------------------------------------------------
STAGE 5 - SOCKET PROGRAMMING (build the foundations of WebSockets)
--------------------------------------------------------------------------------
syscalls: socket(), bind(), listen(), accept(), connect(), recv(), send(),
  close(), setsockopt(), shutdown().
I/O models: blocking, non-blocking, I/O multiplexing (select -> poll -> epoll
  /kqueue), edge-triggered vs level-triggered, and finally io_uring.
Build: echo server -> multi-client chat server -> file transfer -> an HTTP/1.1
  server -> a WebSocket server (implement the RFC 6455 handshake + framing
  yourself; this directly demystifies your current chat app).
+ ADD: zero-copy I/O (sendfile, splice), scatter/gather (writev/readv).

--------------------------------------------------------------------------------
STAGE 6 - CONCURRENCY & PARALLELISM
--------------------------------------------------------------------------------
Threads, async I/O, event loops, multiprocessing, futures/promises, thread pools.
+ ADD (the hard, expert part):
  - Memory models & memory ordering (acquire/release/seq-cst), happens-before.
  - Atomics, CAS (compare-and-swap), the ABA problem.
  - Lock-free & wait-free data structures, false sharing, cache-line padding.
  - Concurrency models: shared-memory + locks, actor model, CSP (Go channels),
    work-stealing schedulers.
Languages: Go goroutines, Rust async/tokio, C++ std::thread/std::atomic.

--------------------------------------------------------------------------------
STAGE 7 - DISTRIBUTED SYSTEMS  *****  (the heart of Kafka)
--------------------------------------------------------------------------------
Replication, leader election, consensus, sharding, partitioning, CAP theorem,
eventual consistency, distributed locks.
+ ADD:
  - Time & ordering: Lamport clocks, vector clocks, hybrid logical clocks.
  - Consistency models: linearizability vs serializability vs causal.
  - Delivery semantics: at-most / at-least / "exactly-once" (and why true
    exactly-once is a myth without idempotency + dedup).
  - Quorums (R + W > N), hinted handoff, read repair, Merkle trees, anti-entropy.
  - Gossip protocols, membership (SWIM), failure detectors.
  - CRDTs, the FLP impossibility result, the two-generals & Byzantine problems.
Algorithms: Raft (start here, it's teachable), Paxos/Multi-Paxos, ZAB, Viewstamped
  Replication.
Resource: MIT 6.824 Distributed Systems - free lectures + labs where YOU build
  a fault-tolerant Raft-based KV store. Do the labs.
Resource: "Designing Data-Intensive Applications" (Kleppmann) - the bible. Read
  it twice.
Resource: The Raft paper + https://raft.github.io visualization.

--------------------------------------------------------------------------------
STAGE 8 - DATABASE / STORAGE INTERNALS
--------------------------------------------------------------------------------
B-Trees, B+Trees, WAL (write-ahead logging), transactions, ACID, MVCC, isolation
levels, indexes, query optimization.
+ ADD: LSM-trees vs B-trees, SSTables, compaction strategies, bloom filters,
  the log-structured storage idea (this IS Kafka's core), write/read/space
  amplification, checksums & corruption handling.
Resource: "Database Internals" (Alex Petrov). Read SQLite and LevelDB/RocksDB.

--------------------------------------------------------------------------------
STAGE 9 - MESSAGE QUEUES & STREAMING (study before rebuilding)
--------------------------------------------------------------------------------
Study: Kafka, RabbitMQ, Redis Streams, NATS, BullMQ, Pulsar.
Concepts: producer, consumer, consumer groups, topic, partition, offset,
  acknowledgements, at-least-once vs exactly-once, backpressure, dead-letter
  queues, retention & compaction, the commit log as the source of truth.
Papers: "Kafka: a Distributed Messaging System", the LinkedIn "The Log" article
  by Jay Kreps.

--------------------------------------------------------------------------------
STAGE 10 - PERFORMANCE ENGINEERING
--------------------------------------------------------------------------------
CPU cache & cache locality, branch prediction, memory allocation & custom
allocators, zero-copy, buffer pools, lock-free programming, SIMD, batching,
mechanical sympathy.
+ ADD (methodology - the expert differentiator):
  - Measure, don't guess. Latency PERCENTILES (p50/p99/p999), never averages.
  - Beware "coordinated omission" (read Gil Tene's talks).
  - Flamegraphs (perf + FlameGraph), USE method, Little's Law.
Resource: Brendan Gregg's "Systems Performance".

--------------------------------------------------------------------------------
STAGE 11 - CORRECTNESS & TESTING (usually skipped; this makes you elite)
--------------------------------------------------------------------------------
- Property-based testing (QuickCheck-style).
- Fuzzing (AFL, libFuzzer, cargo-fuzz).
- Deterministic Simulation Testing (FoundationDB / TigerBeetle style) - run a
  whole distributed system in one deterministic thread and inject faults.
- Jepsen / chaos testing - break real clusters (partitions, clock skew, crashes)
  and check invariants.
- Fault injection, model checking (TLA+ / TLC for verifying protocols like Raft).

--------------------------------------------------------------------------------
STAGE 12 - DESIGN PATTERNS & ARCHITECTURE
--------------------------------------------------------------------------------
Factory, singleton, observer, builder, command, state, strategy.
+ ADD systems-level patterns: reactor & proactor, pipeline, half-sync/half-async,
  circuit breaker, bulkhead, leader/follower, sidecar, event sourcing, CQRS.

--------------------------------------------------------------------------------
STAGE 13 - READ SOURCE CODE & PAPERS (learn the most here)
--------------------------------------------------------------------------------
Source: Redis (very readable C), SQLite, Nginx, Kafka, PostgreSQL, LevelDB/RocksDB,
  etcd (Go + Raft), BullMQ, CPython, Node.js/libuv.
Papers to read (Papers We Love has them): Google GFS, MapReduce, BigTable,
  Amazon Dynamo, Raft, Chubby, Spanner, the Kafka paper.
Skill: learn to read a paper in 3 passes; write a short summary of each.

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
1.  TCP echo server                       (goal: handle 1k concurrent conns)

--------------------------------------------------------------------------------
SUGGESTED HIGH-LEVEL ORDER
--------------------------------------------------------------------------------
Programming (C/Rust/Go) -> DS & Algorithms -> Operating Systems ->
Computer Networks -> Socket Programming -> Concurrency -> Storage/DB Internals ->
Distributed Systems -> Performance -> Correctness/Testing ->
Read + contribute to open-source infra.

--------------------------------------------------------------------------------
YOUR PERSONAL STARTING POINT (given Python + Mongo + queues background)
--------------------------------------------------------------------------------
1. Learn Go (fastest path to infra) OR Rust (if you want to go hardcore).
2. Rebuild your current WebSocket chat server FROM SCRATCH in that language,
   implementing the RFC 6455 handshake and framing yourself. You already know
   the app behavior - now learn the layer beneath it.
3. Build a mini-Redis (RESP + TTL), then add a WAL for persistence.
4. Do MIT 6.824 and build Raft.
5. Then build a persistent commit-log queue and study how Kafka extends it with
   partitions, replication, and distributed coordination.

================================================================================
CAPSTONE  ***  "MiniStream" - a distributed, persistent event-streaming platform
             (a from-scratch Kafka, using EVERYTHING above)
================================================================================
Build a multi-node event streaming system in Go, from the socket up, reusing your
own data structures, storage engine, and Raft. This is a months-long, portfolio-
defining project - the thing that proves you're an infra engineer, not just a user.

CORE REQUIREMENTS
  1. Custom binary wire protocol over TCP (length-prefixed framing) + a WebSocket
     gateway for browser clients (your RFC 6455 code).
  2. Topics split into PARTITIONS; each partition is an append-only commit log on
     disk (segments + index + your bloom filters), with offset-based reads.
  3. Producers with configurable acks (0 / 1 / all); idempotent producer IDs to get
     effectively-once semantics (prove why "exactly once" needs dedup).
  4. Consumers + CONSUMER GROUPS with automatic partition rebalancing and committed
     offsets stored durably.
  5. REPLICATION: each partition has a leader + followers via YOUR Raft; survive the
     loss of a minority of nodes with zero data loss.
  6. Cluster membership + failure detection (heartbeats/gossip); leader election;
     partition reassignment when a node dies.
  7. Retention: time/size-based deletion AND log compaction (keep latest per key).
  8. Backpressure + flow control so a slow consumer can't OOM the broker.

ENGINEERING BAR (this is what makes it "expert")
  - Observability: structured logs, metrics (throughput, p50/p99/p999 latency),
    pprof endpoints, flamegraphs.
  - A deterministic simulation test that runs the whole cluster in one thread and
    injects crashes, network partitions, message reordering, and clock skew, then
    asserts: no committed message is ever lost, offsets never go backwards, and a
    consumer group never skips or double-delivers beyond the guaranteed semantics.
  - A published BENCHMARK (messages/sec, latency percentiles) and a design doc/RFC
    explaining your trade-offs.

STRETCH GOALS
  - Tiered storage (offload old segments to object storage).
  - A simple SQL-ish / KSQL-style query over a topic.
  - Exactly-once transactional writes across partitions.
  - A web dashboard (your WebSocket + chat-app UI skills) showing live topics,
    lag per consumer group, and node health.

WHY THIS PROVES MASTERY - it forces you to combine:
  Go + concurrency (Wk 1-4, Mo 6) · your own DSA (Wk 5-8) · OS/durability (Wk 9-11)
  · sockets/WebSockets (Wk 12, Mo 4-5) · storage engine/WAL/LSM (Mo 7) · Raft &
  distributed systems (Mo 8-9) · queue semantics (Mo 10) · performance (Mo 11) ·
  correctness/fault-injection testing (Mo 12).
